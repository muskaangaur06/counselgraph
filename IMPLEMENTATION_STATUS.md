## Phase 8 Decisions
- DecisionBrief stores its 13 required sections (15.3) as one JSON column rather than 13 separate columns -- they're generated together, displayed together, and nothing queries into an individual section independently. Same reasoning as RiskFlag.deviation_detail/confidence_breakdown already being JSON blobs rather than normalized columns.
- ApprovalStep is a separate table from DecisionBrief, not a JSON array on the brief row, because each step needs its own decided_by/decided_at/comments/required_changes/send_back_reason and independent status transitions (pending -> approved/rejected/etc, or skipped) -- exactly the shape SummaryVersion/ConfidentialityOverride's append-only-row pattern already uses elsewhere in this codebase for "a sequence of independently-timestamped events," just applied to steps within one brief instead of versions of one document.
- DecisionBrief is append-only like SummaryVersion/ConfidentialityOverride: a send_back does not delete or edit the current brief, it creates a new version next time /decision-brief is called and marks the prior brief's superseded_by_version. This means send_back's "creates a new cycle/version" exit criterion is satisfied by the caller re-invoking generation (typically after the reviewer addresses the send-back reason and records more review actions) -- the API does not auto-generate a new version, since a send-back's whole point is that a human needs to act first.
- Approval decisions are enforced against "the current pending step" (get_next_pending_approval_step), not any step the caller names -- 15.4's "only the current assigned approver ... can decide" is read as sequential, not just role-based: even a role that would otherwise qualify can't jump ahead and decide a later step before the earlier one is resolved. can_act_on_assigned_role (already used by Phase 2's review-action authorization) is reused here for the role-seniority check itself, so a senior_counsel/admin covering for an absent junior reviewer can still act on a reviewer-routed step, consistent with how risk-flag routing already works.
- business_head and clo were added to security.py's VALID_ROLES/_ROLE_SENIORITY (ranked above senior_counsel, below admin) rather than inventing a separate approval-only role system -- the existing REVIEWERS roster mechanism (JSON env var or numbered env vars) already supports arbitrary role strings with no code change needed beyond the seniority ranking, so a real deployment can add a business_head/clo account today by just adding a roster entry.
- Evidence validation deliberately checks only monetary figures, not every date/party/clause claim -- see the note in "Current Phase" above. A fabricated dollar figure is the single most consequential and cheapest-to-catch kind of ungrounded statement in a legal brief; broader claim-by-claim NLP grounding would need either a second LLM call (expensive, and itself unverifiable) or a much larger deterministic parser, neither of which section 15.2.4 explicitly demands beyond "every material statement references existing structured data."
- resolve_approval_chain() takes risk_threshold_overrides (org_profile.risk_threshold_overrides, the same JSON dict Phase 6 already uses for senior_counsel routing thresholds) rather than a new dedicated approval-policy table -- reuses an existing per-org config surface instead of adding a new one, consistent with how Phase 6 added value-threshold/governing-law config to the same dict rather than a new table.
- The reject/send_back "stop the chain" behavior (mark remaining pending steps "skipped") was not in my first implementation -- caught by test_reject_marks_brief_rejected_immediately, which asserted get_next_pending_approval_step() returns None after a reject and initially failed because the second step was still "pending" and reachable. Fixed in decide_approval_step() rather than working around it in the API layer, since "a rejected/sent-back brief has no current approver" is a repository-level invariant, not just a UI concern.
- generate_decision_brief_sections() never raises on an LLM failure -- _fallback_brief() returns every section explicitly stating generation failed and defaults the recommendation to "escalate" (the safest of the four allowed recommendations), consistent with confidentiality.py's classify_with_llm never silently defaulting to the least-scrutinized outcome on failure.
- The Decision Brief UI lives inside Review Workspace's existing document-detail render (renderDecisionBriefBlock, appended after the clause list), not a separate screen -- generation and viewing/deciding both happen wherever a reviewer already has the document loaded, since section 15.2's flow starts from "the first reviewer selects Complete Review" and 15.4's next-approver flow is also document-scoped. The blueprint's UI-map note (section 17ish, "Decision Brief can be a sub-tab of Approval & Escalation rather than an unnecessary seventh top-level screen") was satisfied by not adding a new top-level tab; a dedicated Approval & Escalation sub-tab listing every pending brief across documents was not built this phase (see Known Gaps).

## Phase 7 Decisions
- SummaryVersion is append-only by design (like AuditLog/ConfidentialityOverride) -- there was never an UPDATE path for an existing row, only INSERT via add_summary_version(). This already satisfied "do not overwrite approved summary history" structurally before I wrote a line of Phase 7 code; the real work was making that guarantee visible and usable (edit -> new version, restore -> new version, approve -> mutate only that one row's status fields, never its text).
- is_ai_generated is explicit rather than inferred from edited_by being null, even though that's exactly how the initial AI-generated version is distinguished today. Made it explicit because "restore" sets edited_by (a human took the action) but the restored TEXT is often still AI-authored content from an earlier version -- collapsing that into "edited_by is null = AI" would have made restores look human-authored from scratch, which isn't quite right either. Chose to mark every non-initial version (edits AND restores) as is_ai_generated=False, on the reasoning that a human deliberately choosing to bring back or rewrite text is itself the meaningful editorial act being recorded, regardless of the text's origin.
- restore_summary_version() always creates a NEW version (current max+1) with the target version's text, never rewinds version_number or deletes anything after the restored version. This was the explicit blueprint requirement ("old versions remain available") but it's also the only choice consistent with the table being append-only in the first place -- a "true rewind" would have meant either deleting rows (breaking the append-only invariant) or mutating version_number in place (same problem).
- Approval has no role restriction (any authenticated reviewer can call the approve endpoint), unlike Phase 4's confidentiality override (senior_counsel/admin only) or Phase 6's prohibited-language flags. Section 14.1 doesn't specify an approval role restriction the way section 12.3 explicitly did for confidentiality -- didn't invent one not asked for. Revisit if the blueprint's later phases (e.g. Decision Brief / approval chain in Phase 8) turn out to need summary approval gated by seniority too.
- The word-level diff (wordDiff/renderWordDiff in index.html) is a small LCS-based implementation, not a library -- no diff library exists anywhere in this codebase's frontend already, and pulling one in for a single feature felt disproportionate for prose-length summary text (typically a few hundred words). It's O(m*n) which is fine at that length; would need reconsidering if summaries ever grew to full-document length.
- Found and fixed a real pre-existing bug while reading this code path (not something I introduced): the document-detail endpoint read summary_versions[0] as "the current executive summary," but get_summary_history() explicitly documents ascending order (oldest first) -- meaning every session since SummaryVersion existed has shown the ORIGINAL AI summary forever, silently discarding all human edits from view. Flagged this to the user and got explicit confirmation before fixing it as part of this phase (not smuggled in as a side effect) -- see the AskUserQuestion exchange at the start of this phase.

## Phase 6 Decisions
- RiskFlag.clause_id became nullable rather than adding a separate DocumentRiskFlag table -- document-level categories (missing_clause, compliance_gap, value_threshold, unusual_governing_law) are still "a risk flag," just without a single clause to point at. A second table would have meant duplicating severity/confidence/rationale/assigned_role/reviewer_status/audit wiring for no real benefit. The one real cost: existing Postgres tables had clause_id as NOT NULL, so a new explicit migration step (_relax_risk_flag_clause_id in session.py) was needed since _add_missing_columns() only ADDS columns, never alters an existing one's constraints -- verified this against the live container, not just SQLite (SQLite can't ALTER COLUMN at all, so the fast test suite never would have caught a Postgres-only migration bug here).
- clause_id and document_id are strictly mutually exclusive on every RiskFlag row (enforced by convention, not a DB CHECK constraint) -- a clause-level flag reaches its document only via Clause.document_id, never a denormalized RiskFlag.document_id. Caught this the hard way: several of my first-draft deterministic checks set both fields on the same row, which double-counted the flag under a "give me every flag for this document" query (direct document_id match + the clause-join path both matched the same row). Fixed everywhere and locked in with test_clause_level_flags_never_set_document_id.
- The category taxonomy is split by WHERE the detection happens, not arbitrarily: flag_risks()'s LLM prompt only offers the 5 categories an isolated clause's text alone can support (non_standard, ambiguous, prohibited_language, excessive_liability, asymmetric_rights); the other 7 (missing_clause, conflicting_terms, duplicate_clause, compliance_gap, value_threshold, unusual_governing_law, auto_renewal) are produced deterministically elsewhere (missing_clause_node, detect_conflicts_node, graphrag/compliance.py, the mandatory/prohibited standards scan) because they inherently need cross-clause or document-level context a single clause's text can't provide. Both paths write to the same RiskFlag table with applicable_rule_source distinguishing "llm_risk_review" from "deterministic:<check_name>" -- a reviewer sees one unified list either way.
- Deterministic excessive_liability (regex keyword match for "unlimited liability"/"uncapped liability" etc.) runs ALONGSIDE the LLM's own excessive_liability category, not instead of it -- deliberately redundant. The LLM might miss or reword an unmistakable case; the regex is a high-confidence backstop specifically for the unambiguous "the word unlimited is right there" case from section 13.4's required test list, not a replacement for the LLM's broader judgment on subtler cases.
- compliance_gap discovery required a new repository/standards function (find_all_mandatory_and_prohibited in graphrag/standards.py) rather than reusing Phase 5's check_mandatory_and_prohibited() as-is -- that function takes one clause_type and answers "is X mandatory/prohibited," which is fine when checking a clause_type that WAS extracted, but a mandatory standard for a clause_type that's ABSENT from the document (the actual compliance_gap scenario) has no known clause_type to ask about from the extracted-clauses side. The new function scans every clause_type the document's scope has any mandatory/prohibited standard for, independent of what got extracted, then risk_flag_node cross-references that against present_clause_types itself.
- missing_clause_node's checklist-based detection (org_profile.required_clause_checklist, existing since before Phase 5) and the new mandatory-standards-based compliance_gap detection are deliberately two separate mechanisms writing two different categories (missing_clause vs. compliance_gap), not merged into one. They come from different sources of truth (a simple org-profile JSON checklist vs. a KnowledgeReference row with is_mandatory=true) and can disagree -- keeping them separate means a reviewer sees both signals rather than one silently overriding the other.
- format_executive_summary() in contract_metadata.py now also forwards monetary_value (previously computed by extract_contract_metadata() but dropped before reaching document_context) -- needed so risk_flag_node's value-threshold check has a number to compare against without a second LLM call. Checked first that no existing test asserted an exact shape for that function's return dict before adding the field.
- Test coverage for the LLM risk-review path (category="ambiguous" etc.) mocks flag_risks() rather than calling the real Gemini prompt, consistent with how every other LLM-backed path in this repo is tested (extraction, playbook, confidentiality's classify_with_llm) -- the prompt-following behavior itself isn't independently verified by an automated test, same limitation as those other paths.

- No Alembic. Added a small idempotent column-retrofit helper (_add_missing_columns in session.py) that diffs each model's columns against live table columns via SQLAlchemy inspector and ALTER TABLE ADDs what's missing, with the column's Python-side default carried into the DDL so retrofitted existing rows don't end up NULL (e.g. is_active retrofits to true, not NULL).
- seed_defaults() is get-or-create by natural unique key (customer.code, jurisdiction.code) and only backfills org_profile rows where customer_id IS NULL, so a profile already assigned to some other customer is never silently reassigned (tested).

Every document already carries org_profile_id (currently NULL for all 4 existing rows), and customer scope is derivable transitively via org_profile.customer_id. Revisit only if Phase 4/9 tenant-filtered query performance actually needs a direct denormalized index.
- Did not add a DocumentType table this phase -- not blocking anything in Phase 1's scope, deferred to whichever phase first needs it (likely Phase 4/5).
- Query-layer tenant isolation (section 10's negative tests: cross-org access denial, vector-retrieval tenant filtering) is NOT implemented yet -- there is exactly one customer and no auth-role-to-org mapping today, so there is nothing to isolate against. Revisit once Phase 2 (auth/access control) and Phase 5 (tenant-filtered RAG) land.
